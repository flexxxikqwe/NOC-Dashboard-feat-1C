# Спецификация контракта Spool-очереди (1C-NOC Spool Contract v1.0)

## 1. Назначение и разделение ответственности

Контракт Spool определяет протокол взаимодействия между расширением **1С:Предприятие 8.3** (`_МониторСаппорта`) и фоновой службой **1C-NOC Windows Service** (C++/Win32).

### Принцип архитектурного разделения (Zero-Freeze):
1. **Расширение 1С (User-Space / POS):**
   - Собирает исключительно прикладные данные 1С (статус смены, очередь ОФД, критические ошибки Журнала регистрации, версию платформы/конфигурации).
   - **Не выполняет сетевых вызовов** (никаких `HTTPСоединение` к внешним серверам).
   - **Не опрашивает WMI/COM** (никаких вызовов `SWbemLocator` или команд оболочки).
   - **Не хранит и не передает токены авторизации** кассы (токены изолированы в службе Windows).
   - Формирует пакет Spool Envelope v1.0 и атомарно записывает его в локальную файловую очередь spool (< 1–3 мс).
2. **Windows Service (Phase 4.2+, Service-Space / SYSTEM):**
   - Наблюдает за каталогом очереди через `ReadDirectoryChangesW` + резервный таймер.
   - Читает только завершенные `.json` файлы (игнорируя `.tmp`).
   - Валидирует структуру JSON и изолирует поврежденные файлы в `quarantine/`.
   - Дедуплицирует сообщения по SHA-256 и переносит их в локальный кольцевой буфер SQLite (<= 10 МБ).
   - Опрашивает системные метрики ОС (Win32 API) и ID удаленного доступа (AnyDesk/RuDesktop).
   - Прикрепляет Bearer-токен из защищенного реестра и асинхронно передает пакет в NOC Hub (`POST /api/v1/telemetry`).

## 2. Структура файловых путей и каталогов

### Стандартные пути Windows:
- **Корневой каталог очереди:** `%ProgramData%\1C-NOC\spool` (по умолчанию `C:\ProgramData\1C-NOC\spool`).
- **Каталог карантина (Phase 4.2):** `%ProgramData%\1C-NOC\quarantine`.
- **Тестовое переопределение:** переменная среды `NOC_SPOOL_DIR` (для юнит-тестов и стендов).

### Соглашение по именованию файлов:
1. **Временный файл записи (In-Flight):**
   - Шаблон: `temp_<event_id>.tmp`
   - Пример: `temp_a1b2c3d4-e5f6-7a8b-9c0d-1e2f3a4b5c6d.tmp`
   - Служба Windows **игнорирует** файлы с расширением `.tmp` при отборе пакетов.
2. **Готовый файл события (Published / Ready):**
   - Шаблон: `<timestamp_utc_compact>_<event_id>.json`
   - Формат временной метки: `YYYYMMDDHHmmssfff` (UTC), длина 17 цифр.
   - Пример: `20261012143000123_a1b2c3d4-e5f6-7a8b-9c0d-1e2f3a4b5c6d.json`
   - Преимущество: лексикографическая сортировка имен файлов естественным образом соответствует порядку FIFO.

## 3. Схема данных (Spool Envelope Schema v1.0)

Формат файла: **UTF-8 без BOM**, чистый JSON.

### Пример пакета:
```json
{
  "schema_version": "1.0",
  "event_id": "a1b2c3d4-e5f6-7a8b-9c0d-1e2f3a4b5c6d",
  "timestamp_utc": "2026-10-12T14:30:00.123Z",
  "source": "1C_EXTENSION",
  "event_type": "TELEMETRY",
  "priority": "NORMAL",
  "payload": {
    "shop": "Магазин Розница №42",
    "workplace": "Касса 1",
    "warnings": [
      "Кассовая смена открыта более 24 часов (длительность: 26.4 ч.). Необходима Z-инкассация."
    ],
    "runtime_errors": [
      {
        "time": "2026-10-12T14:28:15Z",
        "event": "1C_Runtime_Error",
        "error_text": "Ошибка при вызове метода контекста (ПечатьЧека): ККТ не отвечает."
      }
    ],
    "health_checks": [
      {
        "id": "shift_duration_24h",
        "name": "Длительность кассовой смены",
        "status": "WARN",
        "details": "Кассовая смена открыта более 24 часов."
      }
    ],
    "one_c_info": {
      "platform_version": "8.3.24.1540",
      "configuration_name": "Розница, редакция 2.3",
      "computer_name": "POS-TERM-01"
    }
  }
}
```

### Спецификация полей конверта (Envelope):

| Поле | Тип | Обязательно | Описание |
| :--- | :--- | :--- | :--- |
| `schema_version` | String | Да | Версия схемы конверта (строго `"1.0"`). |
| `event_id` | String | Да | Уникальный GUID события (36 символов с дефисами). |
| `timestamp_utc` | String | Да | Время фиксации события по UTC в формате ISO 8601 (`YYYY-MM-DDTHH:mm:ss.fffZ` или `YYYY-MM-DDTHH:mm:ssZ`). |
| `source` | String | Да | Идентификатор источника (строго `"1C_EXTENSION"`). |
| `event_type` | String | Да | `"TELEMETRY"` (регламентный сбор раз в 10 мин) / `"INCIDENT"` (критическая кассовая ошибка/ККТ) / `"HEARTBEAT"`. |
| `priority` | String | Да | `"NORMAL"` / `"HIGH"` / `"LOW"` (используется для FIFO-вытеснения в SQLite). |
| `payload` | Object | Да | Прикладные данные 1С (содержимое метрик). |

### Спецификация полей полезной нагрузки (`payload`):

| Поле | Тип | Обязательно | Описание |
| :--- | :--- | :--- | :--- |
| `shop` | String | Да | Наименование магазина / торговой точки. |
| `workplace` | String | Да | Наименование кассы / рабочего места кассира. |
| `warnings` | Array[String] | Нет | Список предупреждений (смена > 24ч, буфер ОФД > 10). |
| `runtime_errors` | Array[Object] | Нет | Ошибки Журнала регистрации: `{ time, event, error_text }`. |
| `health_checks` | Array[Object] | Нет | Результаты проверок: `{ id, name, status, details }`. |
| `one_c_info` | Object | Нет | Метаданные 1С: `platform_version`, `configuration_name`, `computer_name`. |

### 4. Ограничения размера и правила усечения (Payload Guards)

1. **Максимальный размер пакета на диске:** строго $\le 64$ КБ ($65\,536$ байт в кодировке UTF-8).
2. **Точный подсчет в байтах:** размер определяется через двоичные данные UTF-8 (`ПолучитьДвоичныеДанныеИзСтроки().Размер()`), а не по длине символов, что исключает ошибки при двухбайтовой кириллице.
3. **Бюджет размера и правила усечения:**
   - Серверный API Ingestion (`POST /api/v1/telemetry`) имеет жесткий лимит `MAX_PAYLOAD_BYTES = 65 536 байт`.
   - Будущая служба Windows внедряет в итоговый запрос служебные данные (`remote`, `system_info` CPU/RAM/диски, заголовки) объемом до 1–2 КБ.
   - **Предупреждающий порог усечения в 1С:** 55 000 байт UTF-8.
   - При превышении 55 000 байт:
     * массив `runtime_errors` ограничивается 5 последними записями, а длина текста ошибки усекается до 300 символов;
     * массив `warnings` ограничивается 5 записями.
   - Если даже после усечения размер пакета превышает 65 000 байт, пакет отбрасывается во избежание передачи поврежденных данных.

## 5. Протокол безопасной записи (Atomic Publish & Crash Recovery)

```
[1С: Процесс кассира]
         │
         ▼
 1. Создание temp_<guid>.tmp на том же NTFS-томе (%ProgramData%\1C-NOC\spool)
         │
 2. Потоковая запись UTF-8 JSON через ЗаписьТекста (без BOM)
         │
 3. Закрытие дескриптора файла (Flush & Close)
         │
 4. Атомарное переименование:
    ПереместитьФайл(temp_<guid>.tmp, <timestamp>_<guid>.json)
         │
         ▼ (Готово для чтения службой)
```

### Защита от накопления мусорных `.tmp` файлов при авариях (Crash Recovery):
1. Штатная обработка исключений в 1С удаляет `temp_<guid>.tmp` при ошибках записи.
2. При внезапном аварийном завершении процесса 1С (обрыв питания, BSOD, принудительное завершение):
   - Расширение 1С при каждом вызове `_МС_ПроверитьГотовностьИЛимитSpool` выполняет поиск и удаление зависших `temp_*.tmp` файлов старше 1 часа.
   - Служба Windows (Phase 4.2) в фоновом цикле выполняет превентивную очистку любых `temp_*.tmp` файлов старше 5 минут.

## 6. Защита от переполнения очереди и гарантии приоритетов (Priority Backpressure Guard)

Если Windows-служба выключена, остановлена или отсутствует:
1. Перед каждой записью 1С проверяет количество готовых `.json` файлов в каталоге spool.
2. **Проблема голодания приоритетов (Priority Starvation) в наивной модели:**
   - Если очередь имеет единый плоский лимит (например, 50 файлов), то регулярная телеметрия (`TELEMETRY` раз в 10 минут) заполнит все 50 слотов за ~8.3 часа.
   - При возникновении критического инцидента кассы (`INCIDENT` / `HIGH`: отказ ККТ, сбой фискализации чека, падение кассовой смены) запись будет отклонена, и критический инцидент будет безвозвратно потерян.
3. **Решение Phase 4.1.2: Приоритетное квотирование слотов очереди (Slot Headroom Reservation):**
   - **Максимальная емкость очереди spool:** 50 файлов `.json` ($\le 3.2$ МБ диска).
   - **Квота регулярной телеметрии (`TELEMETRY` / `NORMAL`):** **40 файлов** (80% емкости очереди). При достижении 40 файлов генерация рутинной телеметрии безопасно подавляется.
   - **Квота критических инцидентов (`INCIDENT` / `HIGH`):** **50 файлов** (100% емкости очереди).
   - **Гарантированный резерв (Headroom):** 10 слотов (файлы 41–50) физически зарезервированы исключительно под аварийные инциденты. Даже при полном заполнении квоты телеметрии инциденты продолжают беспрепятственно публиковаться в spool!
4. **Поведение при абсолютном исчерпании очереди (50 файлов):**
   - Если даже аварийный резерв полностью исчерпан (в очереди 50 готовых файлов, служба не запущена), 1С не прерывает работу кассира, но фиксирует предупреждение в системный Журнал регистрации 1С (`1C_NOC.Spool.QueueOverflow`, уровень `Ошибка`).
5. **Приоритетное вытеснение на уровне службы Windows (Phase 4.2 / Phase 4.3):**
   - При импорте из spool в локальную базу SQLite (буфер $\le 10$ МБ) служба реализует приоритетное вытеснение: при заполнении 10 МБ в первую очередь удаляются старые записи с `priority = 'NORMAL'` / `'LOW'` и `event_type = 'TELEMETRY'`. События `priority = 'HIGH'` не вытесняются рутинными записями.

## 7. Модель прав доступа NTFS ACL и семантика Win32 MoveFileEx

### 7.1. Устранение уязвимости наследования ACE (Аудит Phase 4.1.3):
- **Обнаруженный дефект:** При указании флага наследования `(OI)` (Object Inherit) для группы `Users` (`*S-1-5-32-545`), право `WD` (`FILE_ADD_FILE` на каталоге) транслируется ядром NTFS в `FILE_WRITE_DATA` на всех дочерних файлах. В результате любой непривилегированный пользователь (или чужой процесс кассира) получал возможность модифицировать или перезаписывать готовые файлы очереди других пользователей.
- **Исправление:** ACE для группы `Users` устанавливается **СТРОГО БЕЗ ФЛАГОВ НАСЛЕДОВАНИЯ** `(OI)` и `(CI)` (`AceFlags = 0`, "Только для этой папки"). 
  - На каталог очереди группа `Users` имеет `RD,WD,RA,REA,X,S` (листинг и создание новых файлов).
  - На дочерние файлы группа `Users` **не получает никаких прав** (`FILE_WRITE_DATA` и `FILE_READ_DATA` чужим пользователям не предоставляются).
  - Создатель файла получает права к своему временному файлу через `CREATOR OWNER` (`*S-1-3-0:(OI)(CI)(IO)F`), что позволяет завершить запись и выполнить атомарный перенос (`MoveFileExW` / `ПереместитьФайл`).

### 7.2. Матрица эффективных прав доступа:

| Объект | Субъект безопасности (SID) | Права в icacls | Эффективные права NTFS | Назначение и обоснование |
| :--- | :--- | :--- | :--- | :--- |
| **Каталог** `%ProgramData%\1C-NOC\spool` | `Administrators` (`*S-1-5-32-544`) | `(OI)(CI)F` | `GENERIC_ALL` | Полное администрирование каталога и очереди. |
| **Каталог** `%ProgramData%\1C-NOC\spool` | `SYSTEM` (`*S-1-5-18`) | `(OI)(CI)F` | `GENERIC_ALL` | Фоновая служба Windows: чтение, перемещение в SQLite/quarantine, удаление. |
| **Каталог** `%ProgramData%\1C-NOC\spool` | `CREATOR OWNER` (`*S-1-3-0`) | `(OI)(CI)(IO)F` | *Не применимо к папке* (`IO`) | Шаблон наследования для создаваемых файлов. |
| **Каталог** `%ProgramData%\1C-NOC\spool` | `Users` (`*S-1-5-32-545`) | `(RD,WD,RA,REA,X,S)` *(без OI/CI!)* | `FILE_LIST_DIRECTORY`, `FILE_ADD_FILE`, `READ_EA`, `TRAVERSE`, `SYNCHRONIZE` | **Только для папки:** создание файлов (`WD`), подсчет файлов для Backpressure (`RD`). Без прав удаления (`DC`). |
| **Файл в spool** (`<ts>_<id>.json`, `temp_*.tmp`) | `SYSTEM` (`*S-1-5-18`) | *(унаследовано)* | `GENERIC_ALL` | Служба читает, парсит и удаляет файлы из очереди. |
| **Файл в spool** (`<ts>_<id>.json`, `temp_*.tmp`) | `Administrators` (`*S-1-5-32-544`) | *(унаследовано)* | `GENERIC_ALL` | Административный контроль. |
| **Файл в spool** (`<ts>_<id>.json`, `temp_*.tmp`) | **Создатель файла** (User-creator) | *(унаследовано от CREATOR OWNER)* | `GENERIC_ALL` | Кассир-создатель может записать `.tmp` и переименовать его (требуется `DELETE`). |
| **Файл в spool** (`<ts>_<id>.json`, `temp_*.tmp`) | **Чужие пользователи** (`Users`) | **НЕТ ДОСТУПА** | **НЕТ ПРАВ** (ACE не наследуется) | **Полная изоляция:** чужие пользователи не могут прочесть, изменить или удалить чужое событие! |
| **Каталог** `%ProgramData%\1C-NOC\quarantine` | `Administrators` + `SYSTEM` | `(OI)(CI)F` | `GENERIC_ALL` | Доступ обычных пользователей (`Users`) полностью заблокирован. Изоляция поврежденных пакетов. |
| **Файл** `%ProgramData%\1C-NOC\config.json` | `Administrators` + `SYSTEM` | `F` | `GENERIC_ALL` | Защита токена авторизации. |
| **Файл** `%ProgramData%\1C-NOC\config.json` | `Users` (`*S-1-5-32-545`) | `R` | `GENERIC_READ` | Чтение адреса сервера. Модификация кассиром заблокирована. |

### 7.3. Почему используется нотация Well-Known SID (`*S-1-...`):
В русскоязычных редакциях Windows группы именуются `СОЗДАТЕЛЬ-ВЛАДЕЛЕЦ`, `Администраторы`, `Пользователи`. Использование строковых имен `"CREATOR OWNER"` в `icacls` на русской ОС приводит к фатальной ошибке сопоставления имени учетной записи. Использование канонических Well-Known SID гарантирует надежное применение ACL на любой языковой версии Windows.

### 7.4. Анализ атомарного переименования в NTFS и коллизий:
1. Вызов 1С `ПереместитьФайл(Временный, Готовый)` транслируется в Win32 API `MoveFileExW(Временный, Готовый, 0)` в пределах одного NTFS тома.
2. Ядро Windows NT проверяет право `DELETE` на дескрипторе исходного файла (`temp_<id>.tmp`). Это право гарантировано создателю через унаследованный ACE `CREATOR OWNER:F`.
3. На целевой папке проверяется право `FILE_ADD_FILE` (`WD`), имеющееся у группы `Users`.
4. **Поведение при существующем целевом файле:**
   - Если целевой файл `<ts>_<id>.json` уже существует, `ПереместитьФайл` выбрасывает исключение времени выполнения (в Win32 без флага перезаписи возвращается ошибка `ERROR_ALREADY_EXISTS`).
   - Исключение перехватывается блоком `Исключение` в `_МС_ЗаписатьСобытиеВSpool`: временный файл безопасно удаляется через `УдалитьФайлы`, существующий файл не повреждается, касса продолжает работу без сбоев (Stealth Fail-Safe).
   - Вероятность коллизии практически равна нулю, так как имя содержит метку времени с миллисекундами (17 цифр) и GUID v4 `event_id`.

*Статус проверки:* Статический анализ Win32/NTFS доказан (`PASS`). Реальное применение в среде Windows — `NOT RUN (NEEDS WINDOWS VERIFICATION)`.

## 8. Трансформация конверта службой Windows для Ingestion API (`POST /api/v1/telemetry`)

> ⚠️ **КРИТИЧЕСКИЙ АРХИТЕКТУРНЫЙ КОНТРАКТ:**  
> Служба Windows (Phase 4.2) **НЕ передает Spool Envelope напрямую на сервер**!  
> Серверный эндпоинт `app/api/v1/telemetry/route.ts` ожидает плоский объект с обязательными полями `shop`, `workplace` и `remote`.

### Таблица сопоставления полей (Spool $\to$ Service $\to$ Ingestion API):

| Поле | Источник в 1C BSL | Поле Spool Envelope | Поле Ingestion API | Обязательность в API | Преобразование службой Windows (Phase 4.2) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Версия схемы** | Константа `"1.0"` | `schema_version` | *(служебное)* | Нет | Служба валидирует `"1.0"`; несовместимые версии отправляет в `quarantine/` |
| **ID события** | GUID v4 | `event_id` | *(служебное)* | Нет | Служба использует для SHA-256 дедупликации и отслеживания статуса доставки |
| **Время события** | `yyyy-MM-ddTHH:mm:ssZ` | `timestamp_utc` | *(служебное)* | Нет | Служба фиксирует исходное время 1С для кольцевого буфера SQLite |
| **Источник** | `"1C_EXTENSION"` | `source` | *(служебное)* | Нет | Служба валидирует источник |
| **Тип события** | `"TELEMETRY"` / `"INCIDENT"` | `event_type` | *(служебное)* | Нет | Служба определяет приоритет сохранения в SQLite |
| **Приоритет** | `"NORMAL"` / `"HIGH"` / `"LOW"` | `priority` | *(служебное)* | Нет | Служба использует для FIFO-вытеснения при заполнении 10 МБ буфера SQLite |
| **Магазин** | Наименование из 1С | `payload.shop` | `shop` | **Да** (String) | Извлекается из конверта: `body.shop = envelope.payload.shop` |
| **Рабочее место** | Наименование кассы/РМ | `payload.workplace` | `workplace` | **Да** (String) | Извлекается из конверта: `body.workplace = envelope.payload.workplace` |

## 9. Release Gate

> ⚠️ **КРИТИЧЕСКОЕ ТРЕБОВАНИЕ РЕЛИЗА:**  
> Новое расширение 1С (Phase 4.1) **не должно развертываться на боевые кассы отдельно от совместимой Windows-службы (Phase 4.2)**.  
> До внедрения службы расширение функционирует в режиме ожидания (Fail-Safe Silent Mode), а файлы очереди накапливаются до квоты (40 файлов для телеметрии, 50 файлов для инцидентов), после чего генерация новых пакетов безопасно приостанавливается.

## 10. Топология выполнения 1С, контекст процессов и безопасность

### 10.1. Контекст запуска 1С и права процесса:
1. **Пользовательский контекст:**
   - 1С на кассовом узле запускается как тонкий клиент (`1cv8c.exe`) или толстый клиент (`1cv8.exe`) от имени локального пользователя кассира (например, `.\Cashier1` или `DOMAIN\cashier`), входящего в стандартную группу Windows `Users` (`*S-1-5-32-545`).
2. **Файловый режим (File IB — целевая кассовая топология):**
   - В файловой базе 1С отдельный серверный процесс отсутствует.
   - Все общие модули со свойством «Сервер: Истина» и «Привилегированный: Истина» компилируются и исполняются **внутри пользовательского процесса клиента** (`1cv8c.exe` / `1cv8.exe`) на кассовом ПК.
   - **Критический факт:** «Привилегированный режим» 1С отключает исключительно встроенные ограничения платформы 1С (RLS). Он **НЕ повышает** привилегии процесса в операционной системе Windows!
   - Процесс 1С обладает строго правами непривилегированного пользователя кассира (`Users`). Все файловые операции в `%ProgramData%\1C-NOC\spool` выполняются с этими правами.
3. **Клиент-серверный режим (Client-Server IB):**
   - Клиентский код (`МодульУправляемогоПриложения.bsl`, `_МС_ТихийСтартМониторинга`) запускается в контексте кассира на кассовом ПК.
   - Серверный модуль `_МС_Сервер` исполняется на сервере 1С в процессе `rphost.exe` под сервисной учетной записью службы сервера 1С (например, `USR1CV8`).
   - Процесс сервера `rphost.exe` **не имеет прямого доступа** к локальной файловой системе кассового ПК (диск `C:\` кассы недоступен серверу).

### 10.2. Временные файлы и атомарное перемещение:
1. **Место создания:**
   - Временный файл `temp_<event_id>.tmp` создается **непосредственно в каталоге очереди** `%ProgramData%\1C-NOC\spool`.
   - Это гарантирует нахождение на том же физическом томе NTFS и исключает межтомовое копирование.
2. **Права на временный файл и переименование:**
   - Создание файла выполняется по праву `WD` (`FILE_ADD_FILE`), предоставленному группе `Users` на каталог `spool`.
   - Созданный файл наследует `CREATOR OWNER:F`, предоставляя создателю право `DELETE`.
   - Переименование через Win32 API `MoveFileExW` требует права `DELETE` на дескриптор исходного файла (`temp_*.tmp`) и права `FILE_ADD_FILE` на целевой каталог (`spool`).
   - Оба права гарантированы кассиру-создателю. При этом чужие пользователи группы `Users` не имеют права `FILE_WRITE_DATA` и не могут изменить или удалить чужой файл.
3. **Обработка коллизий целевого файла:**
   - В 1С метод `ПереместитьФайл` при наличии существующего целевого файла генерирует исключение времени выполнения (в Win32 без флага перезаписи возвращается `ERROR_ALREADY_EXISTS`).
   - Код `_МС_ЗаписатьСобытиеВSpool` перехватывает исключение в блоке `Исключение`, удаляет временный `.tmp` файл и возвращает `Ложь`. Существующий файл не повреждается.
   - Имена файлов включают 17-значную метку времени UTC (до миллисекунды) и уникальный GUID v4 `event_id`, что делает коллизии невозможными в штатной работе.

### 10.3. Клиент-серверный режим и архитектурные границы:
1. **Поведение в клиент-серверной базе:**
   - Сервер `rphost.exe` обращается к `_МС_ПолучитьКаталогSpool()`. Если на сервере 1С служба 1C-NOC не установлена, функция возвращает пустую строку `""`.
   - Функция `_МС_ПроверитьГотовностьИЛимитSpool` немедленно возвращает `Ложь`. Вызов `ВыполнитьРегламентныйМониторинг` безопасно завершается (Stealth Fail-Safe).
2. **Каноническая топология:**
   - Проект ориентирован на **автономные узлы касс (POS)** с локальной файловой базой и локальной службой Windows.
   - Для клиент-серверных установок с центральным сервером запись в spool сервера документирована как опциональный режим серверного мониторинга, а запись клиентских событий требует либо локального агента на сервере, либо клиентской файловой прокси-записи.
