# 1C-NOC POS Agent: Глубокий аудит и архитектурный план перехода на изолированную службу

## Резюме аудита и цель

**Цель:** Обеспечить нулевое влияние мониторинга на рабочий процесс кассира в 1С:Предприятие 8.3, гарантировать отказоустойчивость при медленной/отключенной сети, исключить утечки учетных данных и реализовать строгую изоляцию на базе нативной Windows-службы (C++/Win32) с локальной очередью spool и кольцевым SQLite-буфером (до 10 МБ).

---

## Решения и подтвержденные требования

> [!IMPORTANT]
> **Ключевые решения, подтвержденные на этапе интервью:**
> 1. **Архитектура агента на кассе:** Изолированная фоновая служба Windows с файловой очередью spool (1C пишет локальный JSON во временный каталог, служба асинхронно валидирует, буферизует и передает в NOC).
> 2. **Автономность при сетевых сбоях:** Локальный кольцевой буфер SQLite со строгим лимитом размера базы данных до 10 МБ (FIFO-вытеснение устаревших низкоприоритетных метрик при переполнении).
> 3. **Модель удаленного доступа:** Динамическое обнаружение Client ID (AnyDesk / RuDesktop) через парсинг системных конфигураций/stdout в агенте без хранения статических паролей в скриптах установки или открытом коде.

- **В репозитории присутствуют:**

  - `1c/poc_sandbox.bsl` (прототип/песочница с логикой эмуляции)
  - `public/downloads/install.bat` (скрипт автоустановки на кассовый терминал)
  - `public/downloads/support.cfe` (бинарный файл расширения 1С, 8.4 KB)
  - `public/downloads/version.json` (манифест версии расширения)
- **В репозитории отсутствуют (пробел реализации):**
  - Исходный код нативной Windows-службы (C++/Win32).
  - Локальная база SQLite на кассе.
  - Файловый конвейер spool / quarantine на уровне ОС.
  - Механизм фонового IPC между 1С и ОС вне синхронного BSL HTTP-клиента.

### Фактическая цепочка запуска (Boot Chain)
1. **Старт Windows:** Никаких фоновых сервисов мониторинга не запущено.
2. **Запуск 1С кассиром:** Инициализируется `ПриНачалеРаботыСистемы()`.
3. Подключается фоновый таймер ожидания `ОтправитьТелеметриюВФоне()` с интервалом 300 секунд.
4. Выполняется немедленный сбор первой телеметрии (синхронно прямо при открытии рабочего места кассира!).
5. Серверный модуль BSL запрашивает параметры кассы, сериализует JSON и выполняет блокирующий HTTP-запрос `HTTPЗапрос` к NOC Hub.
6. При сбое сети или задержке шлюза касса подвисает на установленный таймаут (2-3 секунды).
7. Если касса закрыта до срабатывания таймера, телеметрия не передается.

## 2. Анализ производительности (Performance Review)

### CPU
- **WMI и COM-вызовы:** В BSL для получения системных сведений о дисках, памяти и процессоре инициируются вызовы через COM-объект `WbemScripting.SWbemLocator`. Это порождает запуск отдельного COM/WMI-провайдера в Windows (`WmiPrvSE.exe`), потребляя до 15-25% CPU слабого Celeron/Atom на протяжении 300–800 мс.
- **Сериализация JSON:** В `ОбщийМодуль_Сервер.bsl` используется ручная сборка структуры и `ЗаписьJSON`. Для пакета метрик затраты CPU умеренные (~5 мс), но выполняются на основном потоке выполнения 1С.

### RAM
- **COM Automation Leaks:** Создание COM-объектов `WScript.Shell` и WMI внутри циклов 1С без гарантированного `COM-объект = Неопределено;` оставляет неосвобожденные дескрипторы и страницы памяти до принудительной сборки мусора платформой.
- **Отсутствие фонового буфера:** Нет накопления в памяти, но создание структур каждый цикл нагружает кучу процесса `1cv8c.exe`.

### Диск и I/O
- **Нагрузка на ИБ:** При обновлении CFE база 1С блокирует таблицы метаданных.
- **Файловый spool (отсутствует):** В текущей схеме BSL не пишет на диск, но при потере сети данные безвозвратно теряются.

### Сеть и Net
- **Синхронный TCP Handshake:** `HTTPСоединение` создает прямое TCP+TLS соединение с таймаутом 2-3 секунды. При потере пакетов (нестабильный 3G/4G модем на кассе) происходит ретрансмиссия SYN-пакетов, задерживая поток выполнения.
- **Потеря данных:** При недоступности сервера попытка отправки сразу отбрасывается.

### Блокировки интерфейса 1С (UI Thread)
- **Файловая база (главный риск):** На кассовых узлах в 90% случаев используется **файловая база 1С**. В файловом режиме директива `&НаСервере` исполняется **в том же самом процессе и потоке, что и клиентский интерфейс**.
- **Зависание сканера штрихкодов:** Если в момент пробития чека срабатывает 5-минутный таймер телеметрии, кассовый интерфейс блокируется на 2–3 секунды. Кассир нажимает клавиши или сканирует штрихкод, события теряются или буферизуются с задержкой, вызывая очереди на кассе.

## 3. Надежность, изоляция и риски безопасности

1. **Утечка токенов и паролей:**
   - В текущем `public/downloads/install.bat` токен сервера и URL захардкожены в открытом виде.
   - Любой пользователь с правами чтения каталога загрузок или логов установки получает постоянный bearer-токен доступа к API мониторинга.
2. **Пароли AnyDesk:**
   - Скрипт установки настраивает неконтролируемый статический пароль AnyDesk через CLI (`--set-password`). Это грубое нарушение безопасности периметра кассовой зоны.
3. **Безопасный режим 1С (Safe Mode):**
   - Расширение требует отключения безопасного режима (`БезопасныйРежим = Ложь`), так как использует внешние вызовы COM/WMI и сетевой доступ. Отключение безопасного режима дает расширению полные права в ОС от имени пользователя 1С.
4. **Устойчивость к сбоям питания:**
   - При внезапном отключении питания кассы незавершенные HTTP-запросы обрываются, состояние в памяти теряется.

│  │   1С:Предприятие 8.3    │             │   1C-NOC Windows Service      │  │

│  │       расширение)       │             │                               │  │
│  │                         │             │  ┌─────────────────────────┐  │  │

│                                                          │               │  │

### Ключевые архитектурные принципы:

1. **Разделение ответственности:**
   - **1С делает только то, что знает только 1С:** события проведения чеков, внутренние ошибки СУБД, версия конфигурации, тайминги кассовых операций. 1С **не делает** сетевых вызовов, не ходит в WMI/COM и не опрашивает параметры Windows.
   - **Windows Service делает системную работу:** опрос CPU/RAM/дисков, чтение статуса AnyDesk/RuDesktop ID из файлов конфигурации (`system.conf` / реестр), управление сетью, повторные отправки, буферизацию.
2. **Атомарный бескомпромиссный Spool:**
   - 1С формирует JSON и сохраняет его во временный файл `spool\temp_<guid>.tmp`, затем вызывает атомарное переименование в `spool\<timestamp>_<guid>.json`.
   - Запись занимает менее 1 мс на диске, не зависит от доступности сети, гарантированно исключает зависание UI.
   - NTFS ACL на каталог `C:\ProgramData\1C-NOC\spool`: полные права у `SYSTEM` и `LOCAL SERVICE`, у группы `Пользователи` (кассир) — только `FILE_ADD_FILE` (запись без возможности модификации или удаления чужих файлов очереди).
3. **Кольцевой буфер SQLite (макс. 10 МБ):**
   - База данных SQLite в режиме `PRAGMA journal_mode = WAL`, `PRAGMA synchronous = NORMAL`.
   - Ограничение размера: служебная таблица `telemetry_queue` с проверкой квоты страницы (page_count * page_size <= 10MB).
   - При переполнении (длительный оффлайн кассы) автоматически удаляются самые старые метрики типа `HEARTBEAT` и `SYSTEM_METRICS`, но **сохраняются** критические ошибки 1С и кассовые инциденты.
4. **Безопасное динамическое обнаружение Remote Access ID:**
   - Агент читает AnyDesk ID напрямую из `%ProgramData%\AnyDesk\system.conf` (параметр `ad.anydesk.id`) или RuDesktop из `%ProgramData%\RuDesktop\config.json`.
   - Никаких паролей в скриптах! При необходимости подключения специалист техподдержки запрашивает разовый доступ через интерактивное подтверждение на кассе или контролируемый централизованный канал.

## 5. Поэтапный план реализации

### Фаза 4.1: Очистка и облегчение BSL-расширения 1С (Zero-Freeze Extension)
- Удалить синхронные `HTTPСоединение` из основного потока 1С.
- Удалить тяжелые COM/WMI вызовы сбора системной информации из `ОбщийМодуль_Сервер.bsl`.
- Внедрить сверхбыстрый модуль записи событий в локальный spool (`КаталогВременныхФайлов` -> атомарный перенос в каталог Spool агента).
- Сохранить обратную совместимость: если служба Windows еще не установлена, 1С работает штатно без падений и ошибок.

### Фаза 4.2: Ядро Windows-службы (C++/Win32 Core & Spool Pipeline)
- Реализация `1C-NOC-Agent` как Win32 Service (`SERVICE_WIN32_OWN_PROCESS`).
- Инициализация NTFS-директорий с явными дескрипторами безопасности (`SECURITY_ATTRIBUTES`, `SetNamedSecurityInfo`).
- Мониторинг очереди через `ReadDirectoryChangesW` + fallback-таймер опроса каталога.
- Строгая валидация JSON с изоляцией битых файлов в `quarantine/`.
- Вычисление SHA-256 хэша для дедупликации повторных сообщений.

### Фаза 4.3: Кольцевой буфер SQLite и транспортная подсистема
- Встраивание SQLite (amalgamation) с контролем доступа.
- Реализация кольцевого механизма FIFO с жестким порогом 10 МБ.
- Асинхронный HTTP-транспорт на базе `WinHTTP` с поддержкой системного прокси, TLS 1.2/1.3 и сжатия gzip.
- Сбор системных метрик средствами нативного Win32 API (`GetSystemTimes`, `GlobalMemoryStatusEx`, `GetDiskFreeSpaceExW`) — суммарное потребление CPU < 0.1%.

### Фаза 4.4: Модуль обнаружения AnyDesk / RuDesktop и безопасность
- Разработка безопасного парсера конфигураций AnyDesk (`system.conf`) и RuDesktop без прав администратора для кассира.
- Удаление хардкода токенов из скриптов: безопасная инициализация через защищенный реестр `HKLM\Software\1C-NOC\Security`.
- Обновление скрипта установки `install.bat` с удалением статических паролей.

### Фаза 4.5: Комплексное тестирование и валидация
- Стресс-тест кассового интерфейса: замер задержки кассовых операций (целевой показатель: 0 мс задержки UI).
- Тест обрыва сети: искусственное отключение соединения на 72 часа, проверка размера файла SQLite (строго <= 10 МБ), проверка сохранения критических ошибок.
- Тест аварийного завершения питания (Crash Recovery): внезапное прерывание процесса записи в spool, проверка автоматического восстановления очереди и отсутствия повреждения базы данных.
